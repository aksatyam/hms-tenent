01
Architecture Drivers & Principles
The forces the structure must answer to

Five business objectives (BRD Sec. 2) and four classes of NFR (BR-NFR-01…04) impose the shape of the system. The dominant driver is SME unit economics at Pool scale — thousands of single-vertical tenants must run profitably on shared infrastructure while a hospital tenant on the same code runs on a dedicated database. Architecture exists to make those two extremes one product.

BRD Sec. 1 · A1

Guiding architectural principles

P1
Tenancy is ambient, never a feature. Every DB access runs under SET LOCAL tenant context with RLS fail-closed; background jobs (Quartz, Spring Batch, Kafka consumers) set context explicitly or fail closed. No service trusts a client-supplied tenant id.
P2
Entitlements gate at four independent layers. A disabled module must be unreachable at gateway route, JWT permission set, service guard and UI nav — defence in depth, no single point of bypass (BR-NFR-03).
P3
One shared core, locked ON. Identity, Registry/UHID, M4 Finance, M9 Audit, M12 Platform Admin and Notifications are non-removable for every edition — the spine that makes upgrades migration-free.
P4
Events are the integration contract. Modules communicate through Kafka with a fixed envelope (tenantId mandatory, partition key = tenantId); synchronous calls are the exception, reserved for read-after-write needs.
P5
Money and stock moves are idempotent. Idempotency keys mandatory on all POST money-moving / stock-moving endpoints; duplicate submission returns the original result, never a double effect.
P6
Degrade gracefully, never silently. When PACS, IRP, ABDM or an analyzer is down, the dependent flow continues in a banner-flagged degraded mode and queues reconciliation — it does not block the revenue path.
P7
Auditability is structural. The audit write is part of the transaction, hash-chained; there is no "audit later" path and no single-person release path for reportable clinical results.

HMSPro sits between healthcare operators (clinical & front-office staff, owners), patients/customers, and a ring of regulated external systems. The VSJ platform team operates it as a control plane above all tenants.

Container View — C4 Level 2
The deployable units and how requests & events move through them

A request enters through the edge, is authenticated and entitlement-filtered, lands on a domain service, mutates tenant-scoped Postgres inside a transaction that also writes the audit row and the outbox, and emits a Kafka event consumed downstream. Reads for dashboards and search are served from Elasticsearch marts, not the OLTP path.

Figure 3.1 — C4 Level 2 Container View. Teal = synchronous request path; gold-dashed = external adapter / event path. The Kafka backbone decouples write-side modules from read-side BI and notifications.

04
Multi-Tenancy & Isolation Architecture
Three isolation models, one API — tier follows the plan

Isolation tier is a property of the subscription plan, resolved at onboarding and stored in tenant_directory (the TAD-003 control plane). The same service code serves all three; only the connection-routing and DDL strategy differ. RLS is the universal backstop — even on dedicated DBs it stays on, fail-closed, so a context bug can never leak rows.

Figure 4.1 — Tiered isolation per TAD-003. RLS is present in all three tiers; the difference is the routing & DDL strategy the provisioner applies.

Tenant context resolution (every request)

  • JWT carries tenantId, isolationModel, clusterId, role & entitlement set — signed, never client-mutable.
  • A request-scoped TenantContext filter resolves the data source / schema from tenant_directory and opens the connection with SET LOCAL app.tenant_id = ….
  • RLS policies on every tenant table compare tenant_id to the session GUC; missing context ⇒ zero rows (fail-closed), never all rows.
  • Async workers (Kafka consumers, Quartz) re-establish context from the event/job header before any DB access, or abort.

Provisioning & migration (UC-M12-01 / 03)

  • Provision: tier-specific playbook — Pool seed rows / CREATE SCHEMA from golden template + RLS + role / CREATE DATABASE + PgBouncer + backup registration.
  • Smoke isolation test: write as new tenant, read as canary, assert zero rows — failure rolls back; tenant never serves traffic.
  • Migrate (edition/tier): dual-write & verify, atomic flip, old location quarantined 7 days then purged; ≤ 15-min read-only window, zero data loss.
  • Region immutable post-creation (residency); change is a formal migration workflow.
Why this matters architecturallyBecause tier is data, not code, an SME tenant can be upgraded by changing routing strategy — the application layer is identical across Pool/Bridge/Silo. This is what makes "upgrade edition with zero data migration" (BR-EDN-04) structurally achievable rather than a special case.

Editions & Entitlement Enforcement
An edition is a bundle; enforcement is four-layered

An edition is a named template that pre-applies a module bundle at onboarding; Super Admin then overrides à-la-carte under the dependency matrix. The same tenant_modules entitlement set drives the gateway, the JWT, the service guards and the UI — so a disabled module is unreachable everywhere within 60 s of a toggle (BR-NFR-03).

06
Event-Driven Backbone
Kafka as the integration contract between modules

Clinical and commercial state changes are published as events; Finance, BI, Notifications and downstream modules subscribe. Every event carries a fixed envelope, is partitioned by tenantId for ordering-per-tenant, and is produced via the transactional outbox so the event and the DB mutation commit atomically — no lost or phantom events.

Event envelope (header convention)

Backbone guarantees

  • Ordering per tenant via tenantId partition key — a tenant's events never reorder across each other.
  • Exactly-once effect through transactional outbox + idempotent consumers (idempotency keys on money/stock).
  • Poison isolation — failed messages route to a per-topic DLQ with replay tooling; one bad event never stalls a partition indefinitely.
  • Entitlement-aware consumers — a consumer for a module disabled for a tenant no-ops that tenant's events (not DLQ).
  • Tenant-dimensioned — every event is queryable by tenantId for blast-radius analysis in incident response (M09).

Identity, access & data protection

  • AuthN: JWT + mandatory MFA enrolment for Tenant Admin; tokens scoped to tenant + entitlements + role; revoked on suspend/migrate.
  • AuthZ: 6-tier RBAC × module matrix (FSD Sec. 3.4) with data-level scoping ("own pts / care team") enforced in addition to role.
  • Encryption: TLS in transit; at-rest encryption on Postgres / object store; field-level for the most sensitive identifiers.
  • Break-glass: BYPASSRLS / emergency views surface in a dedicated review queue requiring retrospective sign-off (M09).

Audit & incident (M09)

  • Hash chain: each audit_entry stores hash_prev + hash; range verification proves non-tampering; a mismatch auto-raises a P1 incident.
  • Dual clocks: incident header runs CERT-In (6 h) and DPDP (72 h) countdowns; template completeness gates filing; notifications archived with delivery proof.
  • Blast radius: tenantId-dimensioned logs/traces identify affected tenants/principals per incident.
  • Consent: immutable, versioned against UHID; consent.revoked propagates (marketing-stop immediate, ABDM HIP/HIU fan-out).
Compliance is structural, not bolted-onThe audit write participates in the same DB transaction as the data mutation — there is no path that mutates clinical/financial data without an audit row, and no single-person release path for reportable lab/radiology results (dual validation enforced by workflow). DPDP safeguard position (isolation + RLS + encryption + audited RBAC) is inherited by every edition (BR-COMP-01).
08
Module Map — C4 Level 3
13 modules + core as bounded contexts

Each module is a bounded context owning its tables and events. The core ring (locked ON) is shared by every edition; the satellite modules are entitlement-gated. M03 has been split from the legacy Laboratory into M03 Pathology and net-new M13 Radiology (BRD A1) — the only structural delta to the hospital scope.

Figure 8.1 — Module map. Core ring is non-removable; satellites are entitlement-gated. Spokes show primary event coupling to core (charges, audit, notifications).
Bounded-context ownership ruleA module reads another module's data only via that module's API or its published events — never by cross-querying its tables. This keeps the schema-per-tenant and dedicated-DB tiers viable and lets a module scale independently.
